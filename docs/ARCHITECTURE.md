# 运行原理

整合直接运行在 Home Assistant 中，不需要额外启动桥接服务。它通过松下中国区云端完成登录、设备发现、状态读取和控制。

## 登录与状态更新

用户在 HA 配置页面输入账号密码后，`Client.login()` 依次完成挑战令牌获取、登录和绑定设备查询。客户端按类别、子类型及必要的型号信息选择支持的设备，并以设备标识的 SHA-256 生成稳定 UID。

`PanasonicCoordinator` 每 60 秒读取一次状态，供 sensor、binary_sensor、switch、climate、select 和 number 六类实体使用。单台查询失败时，该设备显示不可用；全部查询失败时，协调器报告更新失败。首次启动和正常轮询都不会发送控制。

## 控制流程

用户操作实体或 HA 自动化调用服务后，协调器按顺序处理命令。客户端先核对目标和参数，必要时读取最新状态，再由传输层发送请求。命令只发送一次，随后等待并读取状态确认。

命令锁覆盖发送和读回等待，不覆盖全部周期轮询。空调关机在首次未确认后会再延后读取一次，这一步仍是查询，不会再次 SET。

| 模块 | 主要职责 |
| --- | --- |
| `config_flow.py` | 登录、重复账号检查及重新配置 |
| `__init__.py` | 加载、卸载、轮询、命令排队和读回确认 |
| `client.py` | 设备筛选、会话及状态字段整理 |
| `transport.py` | HTTPS 请求、端点限制、超时与证书检查 |
| `protocols.py` | 空调字段、枚举和参数构造 |
| `purifier_protocol.py` | 净化器完整状态与 skip=255 模板 |
| `fridge_protocol.py` | Fridge-19 的 24 字段、温区范围和互斥处理 |
| `entity.py` 及各实体平台 | 设备信息、实体标识和操作入口 |
| `calibration.py` | 默认关闭的脱敏诊断与一次性状态读取 |

## 通信细节

登录沿用云端要求的挑战及 MD5 派生流程，设备 token 使用两层 SHA-512，保留标识后缀的原始大小写。密码由 HA 配置条目保存，会话留在运行内存。

请求固定发送到 `https://app.psmartcloud.com/App/`。通用 `post()` 用于认证、发现和允许的 GET 端点，控制由单独的方法处理。接口名称虽有 GET/SET，实际都通过 HTTP POST 请求。净化器、空调和冰箱的封装不同，适配时需要分别处理。

## 与其他组件的分工

本仓库只维护所列松下设备。其他品牌继续使用各自成熟整合，微信 AI 工具属于可选的上层控制入口。个人面板、自动化、数据库、虚拟机和账号配置都不随本项目分发。

`panasonic_home_readonly` 作为历史 domain 继续保留，避免影响已经建立的实体与自动化。
