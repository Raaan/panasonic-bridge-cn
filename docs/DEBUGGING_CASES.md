# 排障记录

这里整理开发时遇到的几个问题，保留型号、端点、字段和修复思路，供后续适配参考。账号、会话、设备唯一标识和个人配置均已省略。

这些案例记录的是当时的定位过程。净化器、空调和冰箱的现有功能后来均已完成实机确认，当前状态见 [设备说明](DEVICES.md)。

## 净化器可以登录，但没有发现设备

最初沿用社区资料中的 `0830` 类别筛选 F-75C5PJD，结果无法匹配。读取绑定设备信息后，确认它实际使用 `0810/75C5PJD`。

修正类别、子类型和型号匹配后恢复发现。对应测试使用合成设备数据，同时检查 `0830` 不会被误认成此型号。

## 空调状态接口返回失败

通用工具把身份字段嵌入 `params`，沿用了净化器的封装方式。`ACDevGetStatusInfoAW` 实际要求顶层身份字段及 `xtoken: SSID=<SESSION>`，改为单独构造请求后能够读取。

这也说明同一云平台下的接口封装不能直接互换。遇到 `runStatus=49`、`runMode=66` 等值时，需要按对应控制器确认枚举，不能套用旧的 0/1 电源或温度乘二规则。

## 净化器缺少完整模式状态

NeedsAP 实时字段不足以区分四模式和独立等离子体。绑定设备列表的 `statusAll` 提供了扩展字段，其中部分数值以字符串返回。

处理数值字符串后，先校对缓存与实时 `runSta`、`airVo`、`nanoe`，再使用 `runM` 和 `uvSterilization`。缓存不同步时暂不提供对应扩展状态。曾尝试的 `ADevGetStatusODM` 返回 404，未继续猜测 ODM SET。

早期一次消毒切轻柔的详细读回为 `runM: 2 -> 0`、`airVo: 5 -> 1`、NanoeX/等离子体 `1 -> 0`，App 与设备变化一致。后续现有净化器控制也已完成核对。

## 空调灯光没有变化

旧 AW 单字段灯光写入未确认生效。保留参数检查后，改由 `ACDevSetStatusNewProtocol` 发送单字段 `lamp`：

```json
{"params": {"lamp": 0}}
```

这是省略身份信息后的片段。读回从 1 变为 0 时设备灯亮，确认了本机灯光字段的反向含义。其他控制仍按各自载荷处理，不能全部套成单字段请求。

## 冰箱请求受理，但 App 仍显示原状态

其他冰箱系列的载荷不能直接用于 Fridge-19。核对控制资料后，改为 24 字段、`isTodoLimit=1` 和对应会话头；发送前读取状态，校验温区并处理功能互斥，约 12 秒后确认读回。

早期节能导航和快速制冰记录帮助确认了请求格式。后续冰箱现有温控和功能也已完成验证。新增型号仍需注意可选字段默认 0 对其他设置的影响。

## Python 更新后提示证书无效

新版 Python/OpenSSL 的严格 X509 检查曾对旧格式证书报告 `invalid CA certificate`。兼容处理仅用于内置确切指纹的证书，继续保留证书、主机名和有效期校验，不修改系统信任库。

开发稿另加了证书文件防替换检查。证书最初来源仍需独立核对，不能通过关闭 TLS 校验解决后续连接问题。

## 空调关机迟迟未读回

一次关机排障同时遇到设备掉线，网络恢复后设备已关机，单凭当时结果难以区分请求格式与网络影响。代码保留了一次延后读取，不会再次 SET。后续现有空调控制已确认可用，这里保留网络因素对定位的影响。
